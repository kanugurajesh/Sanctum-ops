# Design note: three ways this agent can still do something unsafe

The agent can't do anything the logged-in user couldn't do: identity comes from the JWT, every check is in
code, and tenant isolation is enforced twice (query builders and Postgres RLS). The remaining risks are in
the space the permission model allows. These are the three I'd worry about in production.

## 1. A permitted write hits the wrong rows because the intent was mis-parsed
**How:** policy decides *whether* this user may run `inventory.update`, not *whether this is the set they meant*.
If the LLM drops a filter ("set paracetamol **500mg** to 100" → `name_contains: "paracetamol"`, which matches both
the 500mg and 650mg batches), confuses name with category, or picks `this_month` instead of `last_month`, the
operation is still allowed. Only the preview stands between that and a commit, and people click "confirm"
without reading. The typed row count helps only above 50 rows, and the pharmacist's 500-row cap is the only
hard limit on size. A clarification answer ("yes, all of them") is merged back into the intent by the LLM,
which is another place where scope can quietly widen.
**Next:** show the resolved filter as one plain sentence at the top of every preview, generated by code from
the Operation ("bills dated 1–31 Oct 2026, status ≠ cancelled/refunded, discount < 20%"). Make `scope_all` and
any filter-less write always need typed confirmation, not just writes over 50 rows. Track "preview → cancel →
rephrase" in the audit log as a signal that parsing went wrong, and add those cases to the eval set.

## 2. Money impact isn't treated as a risk dimension
**How:** the guards count rows, not rupees. An admin can give a 100% discount on 40 large bills (₹10+ lakh)
with one click, because 40 is under the 50-row threshold. A billing manager can apply 10% to every bill in
the hospital in one operation, because `bills.discount` has a ceiling but no row cap. Undo can reverse it,
but only until someone touches those bills (e.g. marks them paid). After that, recovery is manual.
**Next:** add ₹-based constraints alongside row caps (`max_impact_inr` per operation and per day), a
two-person rule above a hospital-configurable threshold (the approval routing already exists, so this is a
routing rule, not new machinery), and an alert on the audit stream when a user's cumulative discount impact
for the day crosses a limit.

## 3. Permission semantics can widen access in ways admins don't expect
**How:** when a user holds several roles, constraints combine most-permissively. A user with
`front_desk` (own bills only) plus `billing_manager` sees every bill, which is the right behaviour but
surprising if the second role was meant to be temporary. A permission granted as a per-user override copies
the granter's constraints *at grant time*. If the granter later loses that permission, the grant stays: there
is no cascade and no expiry. "Grant only what you hold" is checked once, at grant time. The demo role switcher
(`/auth/demo-users`, shared password) also has to be turned off (`DEMO_MODE=false`) before real deployment.
**Next:** expiry dates on overrides and on role grants made through the agent; a weekly access-review report
("permissions granted via chat in the last 30 days, and by whom"); an explicit per-permission rule for combining
constraints, instead of one global "most permissive wins"; and SSO-backed sessions with short-lived tokens
instead of the HS256 demo login.

*Not on this list on purpose:* SQL injection, as there's no model-written SQL; cross-tenant reads, as they're
blocked by RLS even if the code had a bug; and prompt injection through data, as the LLM never sees DB rows. Each
of these has a test.
